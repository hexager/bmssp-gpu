## Technical overview: CPU recursion + GPU FindPivots, with CPU and GPU baselines

The BMSSP recursion and data structure D run on the CPU (Castro et al. reference, cpu-v1.4). FindPivots
calls whose first-round edge work is at least a threshold run on the GPU. All other calls use the
built-in CPU FindPivots. Two baselines are measured on the same graphs and sources: a binary-heap
Dijkstra on the CPU, and a device-resident Near-Far SSSP on the GPU with a delta sweep.

## How the GPU FindPivots works

Each FindPivots call runs up to k synchronous Bellman-Ford rounds, with the same semantics as the serial
path of Aniketh's OpenMP v3. One round over the active list:

1. **Pass 1** (one thread per out-edge): each improving proposal does `atomicMin` on the candidate distance.
2. **Pass 2**: proposals with the winning distance do one 64-bit `atomicMin` on `(hops << 32) | pred`.
3. **Commit** (two kernels): write the winner. A vertex whose new key is below B joins the next active list.

The passes read only the state at the start of the round, so the winner is the lexicographic minimum
(distance, hops, predecessor) in any thread order. The commit is split into two kernels so that no
thread reads `root[]` while another writes it. Dropping that split creates a real race that the check catches.

Per round there is one host-to-device copy (edge offsets and active list together) and one small
device-to-host copy (counters, then the new active vertices). Each call ends with one packed copy of the
changed vertices. The per-call log splits the round time into kernel, transfer and host time.

**State ownership.** The CPU changes distances between FindPivots calls. `updateDist()` records every
vertex it changes, and before each GPU call only those vertices are uploaded; the first GPU call of a
run uploads everything. After the call, only the vertices the GPU changed are copied back.

**Change since v1.** In v1, an empty dirty list was passed as a null pointer, which the upload treats
as "all vertices". This caused 2 or 3 extra full uploads per run (at most about 5 ms per run on RMAT20).
`tests/test_full_upload_once.sh` reproduces it on v1 and passes on v2.

## GPU Near-Far baseline

Delta-stepping with two buckets (Davidson et al., IPDPS 2014), fully on the GPU. Near phase: a CUB
exclusive scan of the frontier degrees gives one thread per frontier edge; each thread does `atomicMin`
on the distance and appends an improved vertex to the next near frontier (distance below the split) or to
the far pile. Far phase: when the near frontier is empty, the split moves up by delta and far entries in
the new window become the near frontier. `bin/nearfar GRAPH SOURCE x0.25,x1,x8` runs a warm-up and then
each delta (here 0.25, 1 and 8 times the average edge weight) once, and stops with exit code 5 if two
deltas give different distances.

## Time breakdown (D replay)

`bin/breakdown` runs BMSSP twice. The first run gives the reference implementation's own phase timers. The
second run records every operation on D (initialize, insert, pull, erase, batch prepend). The recording is
then replayed on fresh D objects and timed per kind of operation. Timers around single operations would
distort the run (they added about 50% on NY), so they are not used. Each replayed pull is compared with the
recorded one (bound and an order-sensitive hash of the pulled vertices). Any difference stops with exit 3,
and so does any difference between the BMSSP and Dijkstra distances. Three planted replay bugs (a skipped
erase, 1% of inserts skipped, a skipped batch prepend) are each caught on NY and R-MAT16. The replay runs
on its own, so its caches differ from the real run. On the laptop, the ratio of replayed to in-run pull and prepend time has a median of
0.88 to 1.06 per graph (single runs 0.68 to 1.21).

## Several sources at once (batched FindPivots)

`bin/fp_multi` runs one BMSSP search per source, each in its own CPU thread. FindPivots calls go to one GPU
worker thread. When the GPU is free, the worker takes every call that is waiting and runs them as one batch.
The searches are treated as disjoint copies of the graph (vertex v of search i is i*n + v), so one set of
kernel launches serves the whole batch, and each call keeps its own bound, early exit, W and P. The GPU uses
blocking synchronization, so a waiting thread sleeps instead of spinning on a core.

A batch shares the fixed cost of a call between searches, but each search still waits for its own call to
finish. So batching only helps when other searches can use the CPU during that wait, which needs more
searches than cores. The scenario `8@2` (8 searches on 2 physical cores) tests this; `5@0` (5 searches, all
cores) does not oversubscribe. `scripts/predict_multi.py` predicts both from the single-source data.

## Step by step on the GPU machine

```bash
# 0. Activate the CUDA environment from last time (every new terminal):
eval "$(~/.local/bin/micromamba shell hook -s bash)" && micromamba activate ~/bmssp-cuda
nvcc --version                    # should print release 13.0

# 1. Clone and enter the repository
git clone <this repository> && cd bmssp-gpu

# 2. Graphs (not in git): copy NY, Grid500 and R-MAT16 from team/siddharth-baselines' data set, or run
scripts/make_graphs.sh PATH/TO/bmssp-baselines/data      # generates R-MAT18/20 and checks all five hashes

# 3. Build for the GPU in this machine
make clean all

# 4. Correctness. Must end with "ALL PASS" (about 5-10 minutes).
tests/test_full_upload_once.sh bin/fp_hybrid
scripts/check_all.sh

# 5. Benchmark (about 45-60 minutes). On AC power, other apps closed.
python3 scripts/bench.py --reps 5

# 5b. Time breakdown against Dijkstra (CPU only, about 5 minutes)
python3 scripts/breakdown.py

# 5c. Batched FindPivots: correctness (about 10 minutes), then benchmark (about 30 minutes)
scripts/check_multi.sh                       # must end with "ALL PASS"
python3 scripts/bench_multi.py
python3 scripts/summarize_multi.py results/multi results/multi_prediction.md

# 6. Tables and figures
python3 scripts/summarize.py results/bench
python3 scripts/model.py results/bench

# 7. Send back: zip of results/
zip -r results_v2.zip results
```

## Already verified without a GPU (emulation build)

The emulation build runs every kernel as a loop over its threads in a shuffled order, so it tests the
algorithm and indexing, not hardware races. The real GPU run of step 4 covers races.

- `scripts/check_all.sh` with the emulation builds passes 288 of 288 runs: 149 BMSSP runs (5 graphs x 5 sources,
  mixed dispatch with dirty and full upload, 38 fuzz graphs x 3 sources) with 47,271 GPU-path calls, and 139 Near-Far runs. Every GPU-path FindPivots call is compared with the CPU synchronous version (P, W order, and
  all of d, pred and path_sz). Near-Far is run with 11 deltas per (graph, source) and compared with Dijkstra.
  The log is `results/emulation_verification/check_all_emulation_v2.txt`.
- `scripts/check_multi.sh` with the emulation build: 91, batched calls compared: 94984, result: ALL PASS (5 graphs x 3 settings with 5 sources, 38 fuzz graphs x 2 settings with 3 sources). Planted bugs (root from another search, bound of another search, write-back to the wrong search, early exit that does not stop) are each caught. Log: `results/emulation_verification/check_multi_emulation.txt`.
- Mutation tests: a planted predecessor bug in FindPivots is caught on call 4; a planted root race is
  caught in 2 of 228 fuzz runs; a planted off-by-one in the Near-Far far phase is caught in 65 of 76 fuzz runs.
- The CUDA 13.0 compiler builds both GPU programs for sm_75 with no warnings.

## Configuration reference

| Variable | Values |
|---|---|
| `FP_MODE` | `builtin`, `sync`, `gpu`, `check` |
| `FP_GPU_MIN_EDGES` | threshold on first-round edge work (default 4096; 0 = every call on the GPU) |
| `FP_GPU_DIRTY` | 1 = upload only CPU-changed vertices (default); 0 = full upload on every GPU call |
| `FP_GPU_PIN` | 1 = page-lock the solver state arrays (default) |
| `FP_CALL_LOG` | path of a per-call CSV |
| `BMSSP_CHECK` | 1 = check the FindPivots invariants on every call |
| `FP_EMU_SEED` | emulation builds only: seed of the shuffled thread order |
